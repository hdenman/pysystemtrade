## Context
Determine, for the nominal-capital-500k production system under `~/algo-trading/pysystemtrade/systems/hdenman/production`, whether its currently traded instruments are under-diversified, define a repeatable general assessment, and recommend the next instrument to add. The assessment must refresh rather than blindly reuse the published static-selection ordering, because that report may be stale and recent market moves such as the reported KOSPI crash may change implementation risk or data quality.

## Approach
1. Treat the eight keys in `systems/hdenman/production/system.yaml:instrument_weights` as the held seed portfolio: `EUR_micro`, `GOLD_micro`, `EUROSTX`, `BUND`, `SP500_micro`, `US10`, `CRUDE_W_micro`, and `CORN`. Record the runtime capital/base currency if available, but run the comparison at the requested nominal EUR 500,000, 20% volatility target. Do not change the strategy YAML, weights, IDM, production databases, or positions; this execution produces an assessment and recommendation only.
2. Create `/tmp/next-instrument-assessment.py` as a disposable, read-only analysis driver with CLI `--config`, `--capital`, `--target-count`, and `--json-output`. Load `Config("systems/hdenman/production/system.yaml")`, save the configured held set, delete only the in-memory `instrument_weights` element with `delattr`, set `config.instruments` to the filtered data-backed universe, and construct the system with `get_sim_data_object_for_production(dataBlob())` plus `systems.provided.futures_chapter15.basesystem.futures_system`. This preserves the production system's six EWMAC rules while avoiding `System._get_raw_instrument_list_from_config()` restricting calculations to the existing eight.
3. Build the candidate universe from `diagPrices.get_list_of_instruments_in_multiple_prices(ignore_stale=False)` intersected with instruments that have non-empty adjusted prices. Apply `System.get_instrument_list(remove_duplicates=True, remove_ignored=True, remove_trading_restrictions=True, remove_bad_markets=True, remove_short_history=True, days_required=750)`, subtract `get_list_of_stale_instruments()`, and require each candidate's adjusted and multiple price series to end no earlier than the oldest end date among the eight held series. Abort rather than rank if the held-series end dates differ by more than two business days or their common cutoff is more than five business days old. Record every exclusion and reason; missing values are exclusions, never zero-cost or zero-risk fallbacks.
4. Apply current operational filters before portfolio scoring. Reuse `get_data_for_markets()` from `sysproduction/reporting/data/duplicate_remove_markets.py` and retain rows with `SR_cost <= 0.01`, `contracts >= 100`, and `risk >= 1.5` million base-currency annual-risk units per day, matching `sysproduction/reporting/data/constants.py`. Require `get_instrument_object_from_config(code)` from `sysbrokers/IB/config/ib_instrument_config.py` to resolve static IB symbol/exchange metadata. Keep the generic `minimum_capital_table` only as a diagnostic because its 25% risk, 4% weight, IDM 2.5, and four-contract assumptions do not match this strategy.
5. Score the current set and every feasible one-instrument addition with the existing `SR_for_instrument_list(system, corr_matrix, instrument_list, minimum_instrument_weight_idm)` in `systems/provided/static_small_system_optimise/optimise_small_system.py`. For direct comparability with the repository's nominal-500,000 report, use its target count 28: `max_instrument_weight = 1 / 28`, `notional_starting_IDM = 28 ** 0.25`, and `minimum_instrument_weight_idm = max_instrument_weight * notional_starting_IDM`. The scorer supplies hand-crafted correlation weights, caps IDM at 2.5, assumes pre-cost SR 0.5 for every market, subtracts subsystem turnover times SR cost per trade, and applies `0.125 / maximum_position**2` with positions below 0.5 contracts made effectively untradeable. Sort by expected portfolio SR descending and instrument code ascending for deterministic ties.
6. Quantify diversification rather than inferring it from instrument count. Output the held-set expected SR, each candidate's expected SR and delta, hand-crafted risk weight, resulting IDM, maximum position at forecast 20, size penalty, subsystem turnover, SR cost per trade, liquidity in contracts/risk units, asset class from `diagInstruments.get_asset_class`, mean/maximum absolute correlation to held markets, and data end date. Label the set `under-diversified under the static-selection model` only when the best feasible addition has a strictly higher expected portfolio SR than the held set; otherwise label it `at the model's strict optimum`, while also showing whether additions remain inside the article's 10%-from-peak tolerance.
7. Extend the same conditional greedy step from the held eight until the next best addition falls below 90% of the maximum expected SR seen on that path, matching the published stopping rule. Report the accepted path and the strict maximum point separately; this answers how many instruments current local data can support without claiming that the published 46-instrument list is presently feasible.
8. Measure staleness and regime sensitivity without selecting on realised returns. Repeat the one-addition ranking at EUR 400,000 and EUR 600,000, and with the instrument correlation estimator's `ew_lookback` changed in memory from the configured 25 weeks to 250 weeks with `min_periods: 52`; keep `floor_at_zero: false` as required by the static scorer. The current-score winner remains authoritative; report its ranks in all three sensitivity runs and lower confidence if it leaves the top three. A crash is not itself an exclusion or negative-alpha signal: it matters only through refreshed volatility/maximum position, risk-adjusted cost, liquidity, correlation, and data completeness.
9. Select the highest current-score candidate whose addition improves expected SR and whose local health checks pass at the held-data cutoff. Reuse `check_adjusted_prices`, `check_multiple_prices`, `check_roll_parameters_and_calendar`, `check_expected_contracts`, `check_contract_prices`, `check_fx_prices`, and `check_universe_membership` from `util/check_instrument.py`, passing `held_data_cutoff` as `today` where accepted; reject a candidate only for a `FAIL`, while recording `WARN` details, and continue down the ranking. For the selected candidate, also run the CLI health check at the real current date and store its exit code as deployment readiness rather than changing the analytical recommendation: exit 0 means `ready`, nonzero means `requires-current-data-refresh`. If all improving candidates fail at the common cutoff, recommend no addition. If IB Gateway is reachable, additionally resolve the current contract through `dataBroker.get_brokers_instrument_with_metadata`; if unavailable, retain the recommendation but label live broker qualification as pending because static IB mapping was already required.
10. Write `/tmp/next-instrument-assessment.json` with top-level fields `as_of`, `capital`, `base_currency`, `held`, `held_data_cutoff`, `baseline`, `excluded`, `ranking`, `conditional_path`, `sensitivities`, and `recommendation`, then deliver the general method, full exclusion/ranking table, conditional path, sensitivity table, and one recommendation in the final response. Each exclusion is `{instrument, reason, observed, required}`; each ranking row carries every metric named in step 6; `recommendation` contains `{instrument, delta_sr, health_exit_code, readiness, confidence, broker_qualification}`. Use the January 12, 2026 published list only as a comparison column because its USD capital, system rules, and data vintage differ from this EUR EWMAC system. State the grounded prior before recomputation: `WHEAT` is the first non-held name in that published nominal-500,000 order with local adjusted and multiple prices current through 2026-09-09; `COPPER-micro` ends 2025-09-23 and `KOSDAQ` ends 2024-03-29, while `KOSPI_mini` also ends 2025-09-23, so none can be promoted from that report without refreshed local data.

## Verification

The command must exit 0 and the JSON must show capital `500000`, base currency `EUR`, exactly the eight configured held instruments, a held-data cutoff no more than five business days old, at least one explicitly accepted or rejected candidate, and no NaN/Infinity score serialized as a valid metric.
3. A nonzero current-date result blocks deployment but does not replace a candidate that passed at the common analytical cutoff; if every improving candidate fails at that cutoff, the observable result is `recommendation.instrument: null` with all failures recorded.
5. Re-run the assessment command unchanged. Compare the two JSON payloads after ignoring only `as_of`; held set, exclusions, scores, ranks, path, and recommendation must match, proving deterministic selection from the same data snapshot.

## Assumptions & contingencies
- `Currently traded set` means the eight nonzero configured instrument weights, not instruments with incidental live positions. Actual account capital/currency are reported only as diagnostics; nominal EUR 500,000 remains the selection input.
- This is an analysis-only execution: no source-controlled file, production configuration, database record, position, or order is changed. The disposable script and JSON live under `/tmp`.
- If the held data itself fails the recency/consistency gate, do not substitute the GitHub ordering or silently relax freshness. Deliver `no defensible current recommendation`, name the stale held series and dates, and identify a normal production price refresh as the prerequisite for rerunning this plan.
- If the current-score recommendation leaves the top three in any sensitivity run, still report it as the model winner but set `confidence: low`; otherwise set `confidence: normal`. Set current-date readiness to `ready` only for CLI exit 0 and otherwise to `requires-current-data-refresh`. If IB Gateway is unavailable, set `broker_qualification: pending-live-check`; missing static IB configuration remains a hard exclusion.
